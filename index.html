Parte 1

Fundamentos do Compose

Antes dos desafios, vale entender por que o Compose funciona do jeito que funciona. Cada tópico abaixo é a peça de teoria por trás de uma linha que você já escreveu (ou vai escrever) nos roteiros.

Declarativo conceito-base

No modelo imperativo (o Android "clássico" com XML + findViewById), você dá ordens passo a passo: "ache esse TextView, agora mude o texto dele". Você é responsável por manter a tela sincronizada com os dados manualmente.

No modelo declarativo do Compose, você não diz como mudar a tela — você descreve como a tela deve se parecer para um determinado estado. Quando o estado muda, o Compose recalcula essa descrição e atualiza só o que precisa. É a mesma lógica de uma fórmula de planilha: você não diz "apague a célula e escreva de novo", você escreve =A1+A2 e ela se atualiza sozinha.

💡

Por isso a assinatura do site: toda tela em Compose pode ser resumida na equação UI = f(state). Fixe essa ideia — ela explica praticamente todo comportamento "estranho" que você vai encontrar no Compose.

imperativo (XML)
val tv = findViewById<TextView>(R.id.contador)
var cliques = 0

botao.setOnClickListener {
    cliques++
    // VOCÊ lembra de atualizar a tela
    tv.text = "Cliques: $cliques"
}
declarativo (Compose)
var cliques by remember { mutableStateOf(0) }

Text("Cliques: $cliques")
Button(onClick = { cliques++ }) { ... }
// o Compose atualiza o Text sozinho

Repare: na versão XML, se você esquecer a linha tv.text = ..., a variável cliques muda mas a tela não — é um bug silencioso clássico. Na versão Compose, essa sincronização é automática porque o Text está declarado em função do estado, não escrito uma vez só.

Single-Activity Architecture arquitetura

Jeito antigo (XML + Intents): cada tela era uma Activity própria, declarada no AndroidManifest.xml. Navegar = criar uma Intent e pedir ao sistema operacional para abrir uma nova janela/processo.

Isso gera pilha de navegação (backstack) gerenciada pelo SO, alto custo de memória por instanciar múltiplas Activities, e "Callback Hell" para passar dados de uma tela pra outra.

Jeito moderno (Compose + Estado): existe uma única Activity (a MainActivity). "Navegar" é apenas trocar o valor de uma variável de estado — nenhuma Activity nova é criada.

Quando o estado muda, o Compose recompõe: destrói a árvore de UI antiga e monta a nova, tudo dentro do mesmo processo, em milissegundos.

MainActivity.ktpadrão usado nos 3 roteiros
enum class Tela { MENU, TELA_A, TELA_B }

class MainActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContent {
            var telaAtual by remember { mutableStateOf(Tela.MENU) }
            when (telaAtual) {
                Tela.MENU   -> TelaMenu(onNavegar = { destino -> telaAtual = destino })
                Tela.TELA_A -> TelaA(onVoltar = { telaAtual = Tela.MENU })
                Tela.TELA_B -> TelaB(onVoltar = { telaAtual = Tela.MENU })
            }
        }
    }
}

Funções Composable sintaxe

A anotação @Composable transforma uma função Kotlin comum em um "bloco de construção de UI". Três regras práticas:

RegraO que significa na prática
Nome em PascalCasePor convenção, funções @Composable que emitem UI usam maiúscula inicial (TelaMenu, não telaMenu) — sinaliza que ela "é" um componente, não uma função utilitária comum.
Sem valor de retorno útilUma Composable não "retorna uma View", ela emite UI como efeito colateral controlado. Por isso o tipo de retorno normalmente é Unit (implícito).
Pode ser chamada só por outra ComposableVocê não chama TelaMenu() de dentro de uma função Kotlin qualquer — só de dentro de setContent { } ou de outra função @Composable.

Estado & Recomposição o coração do compose

Três peças trabalham juntas nesta linha, que você já viu nos três roteiros:

Anatomia da linha
var cliques by remember { mutableStateOf(0) }
PeçaPapel
mutableStateOf(0)Cria um "envelope observável" contendo o valor 0. Quando o valor de dentro muda, o Compose é avisado automaticamente.
remember { }Sem isso, a cada recomposição a variável voltaria ao valor inicial. remember diz ao Compose "guarde esse envelope na memória entre recomposições, não recrie do zero".
by (property delegation)Açúcar sintático do Kotlin: sem o by, você acessaria o valor com cliques.value. Com by, você usa cliques diretamente — mas exige importar getValue/setValue.
⚠️

Erro clássico: "Type mismatch: inferred type is Unit but Tela was expected". Quase sempre é falta destas duas importações no topo do arquivo:

import androidx.compose.runtime.getValue
import androidx.compose.runtime.setValue
🔁

Recomposição não é "redesenhar tudo". O Compose é inteligente o bastante para recompor só as funções Composable que realmente leem o estado que mudou — é por isso que no laboratório lá em cima, só o Text pisca, não a tela inteira.

State Hoisting padrão de projeto — aprofundado

Elevação de Estado: uma tela filha não deve guardar (nem saber alterar) o estado que pertence ao "dono" da navegação. Ela apenas emite eventos através de callbacks recebidos por parâmetro, e quem decide o que fazer é quem está um nível acima.

Isso não é uma regra estética — é a consequência direta de como a recomposição funciona (seção anterior). Vamos construir esse conceito do zero, em passos, em vez de só mostrar o resultado final.

Passo 1 — a versão ingênua (estado "preso" dentro do Composable)

Todo mundo começa escrevendo Composables assim: o estado nasce e morre dentro da própria função.

ContadorIngenuo.ktfunciona, mas tem um teto
@Composable
fun ContadorIngenuo() {
    var cliques by remember { mutableStateOf(0) }
    Column {
        Text("Cliques: $cliques")
        Button(onClick = { cliques++ }) { Text("+1") }
    }
}
⚠️

Por que isso não escala: ninguém fora de ContadorIngenuo consegue ler quantos cliques houve, resetar o contador, ou reagir a uma mudança (ex: desbloquear um botão "Salvar" quando cliques > 0). O estado está encapsulado demais — ele virou uma "caixa preta".

Passo 2 — "elevando" o estado um nível acima

A técnica: tire o remember { mutableStateOf() } de dentro do Composable e transforme-o em dois parâmetros — um para ler o valor atual, outro para pedir uma mudança. A função vira "burra" (stateless): ela só exibe o que recebe e avisa o que aconteceu.

Contador.ktagora é "stateless" — não guarda nada sozinho
@Composable
fun Contador(
    cliques: Int,                    // 1. LÊ o estado — não cria
    onIncrementar: () -> Unit          // 2. PEDE uma mudança — não muda sozinho
) {
    Column {
        Text("Cliques: $cliques")
        Button(onClick = onIncrementar) { Text("+1") }
    }
}
MainActivity.kt (ou tela pai)quem chama agora É o dono do estado
var cliques by remember { mutableStateOf(0) }

Contador(
    cliques = cliques,
    onIncrementar = { cliques++ }   // a decisão de COMO mudar fica aqui
)
💡

O que ganhamos: agora quem chama Contador pode ler cliques a qualquer momento, resetar (cliques = 0), limitar (if (cliques < 10) cliques++), ou até ligar o mesmo Contador a duas fontes de estado diferentes em telas diferentes. A função virou reutilizável porque parou de tomar decisões sozinha.

Fluxo Unidirecional de Dados (UDF)

Esse padrão "valor desce, evento sobe" tem nome — é a mesma ideia por trás do value / onValueChange de todo TextField que você já usou:

state ↓ desce · event ↑ sobe

Contador

Escolhas técnicas: até onde elevar?

Um erro comum de quem acabou de aprender State Hoisting é achar que todo estado deve subir até a MainActivity. Não deve. A regra é: eleve o estado até o "ancestral comum" mais baixo que realmente precisa dele — nem mais, nem menos.

EstadoOnde deve morarPor quê
telaAtual (navegação)MainActivityToda tela do when depende dele — é literalmente o ancestral comum de todas.
peso / altura (TelaIMC)dentro da própria TelaIMCNenhuma outra tela do app precisa saber o peso digitado. Subir isso até a MainActivity só adicionaria parâmetros inúteis no caminho todo.
"dropdown está aberto?"dentro do próprio componente do dropdownÉ detalhe de apresentação puramente local — nenhuma regra de negócio depende disso.
🧭

Pergunta-guia: "quem além de mim precisa ler ou reagir a este valor?". Se a resposta é "ninguém", o estado fica local com remember. Se a resposta é "meu componente irmão também precisa", suba até o pai comum dos dois — e pare ali.

Padrão Stateful / Stateless (opcional, mas comum em código real)

Em projetos maiores é comum ver dois Composables para a mesma tela: um "Stateful" (dono do estado, chamado pela Activity) e um "Stateless" (recebe tudo por parâmetro, fácil de testar e de dar @Preview). Aplicando isso ao TelaAgua do roteiro de saúde:

Versão stateful — a que a MainActivity chama
@Composable
fun TelaAgua(onVoltar: () -> Unit) {
    var copos by remember { mutableStateOf(0) }
    TelaAguaConteudo(
        copos = copos,
        onBeberCopo = { copos++ },
        onVoltar = onVoltar
    )
}
Versão stateless — a que você testa e prevê isoladamente
@Composable
fun TelaAguaConteudo(
    copos: Int,
    onBeberCopo: () -> Unit,
    onVoltar: () -> Unit
) {
    Column {
        Text("Total: ${copos * 250}ml")
        Button(onClick = onBeberCopo) { Text("Beber 1 Copo") }
        OutlinedButton(onClick = onVoltar) { Text("Voltar") }
    }
}

@Preview(showBackground = true)
@Composable
fun TelaAguaPreview() {
    // preview usa dados fixos — não precisa de estado real
    TelaAguaConteudo(copos = 4, onBeberCopo = {}, onVoltar = {})
}
⚖️

Trade-off honesto: separar em duas funções deixa o código mais testável e mais fácil de dar Preview com dados fixos — mas também dobra o número de funções e de parâmetros para manter em sincronia. Para os desafios dos roteiros (escopo pequeno, sem testes automatizados), uma única função com State Hoisting simples já é suficiente — o padrão Stateful/Stateless compensa mais em telas grandes ou em projetos com testes unitários de UI.

💡

Regra prática para os roteiros: se uma função Composable recebe onAlgumaCoisa: () -> Unit como parâmetro, isso é State Hoisting em ação — ela "sobe" a responsabilidade da decisão para quem a chamou.

Navegação com Enum + when padrão de projeto

Sem bibliotecas de navegação (como o Navigation Component), um enum class funciona como o "mapa de rotas" do app, e a expressão when na MainActivity funciona como o "roteador": para cada rota possível, decide qual Composable desenhar.

🗺️

É exatamente o padrão usado nos três roteiros: TelaSaude, TelaFinanceira e Tela (miniaplicativos) — mesmo mecanismo, nomes diferentes.

Modifiers sintaxe

Modifier é como você decora e posiciona um Composable — tamanho, padding, fundo, clique, etc. — sem criar um parâmetro novo pra cada característica visual. Pense nele como uma cadeia de instruções aplicadas em ordem.

A ordem importa
Modifier
    .padding(16.dp)     // 1. respiro por fora, depois
    .background(Color.Blue) // 2. pinta o que sobrou
    .fillMaxWidth()      // 3. ocupa a largura disponível
⚠️

Trocar a ordem muda o resultado visual: .background().padding() pinta a área toda antes de abrir espaço; .padding().background() pinta só a área já reduzida. Sempre leia um Modifier de cima para baixo, como uma receita.

.padding(16.dp).background(azul)

O espaço em volta fica sem cor — o padding "empurrou" a área antes de pintar.

.background(azul).padding(16.dp)

A cor pinta a área toda primeiro — o padding só empurra o conteúdo de dentro.

Combo comum nos roteiros
Modifier
    .fillMaxSize()               // ocupa a tela toda
    .padding(24.dp)             // respiro nas bordas da tela
    .verticalScroll(rememberScrollState()) // rola se o conteúdo não couber

Três desses merecem código, porque resolvem problemas estruturais que os componentes dos roteiros não cobrem:

ComponenteProblema que resolve
LazyColumnUma Column comum desenha todos os itens de uma vez, mesmo os fora da tela — péssimo para listas longas. A LazyColumn só compõe o que está visível (como o RecyclerView do XML, mas declarativo).

    items(exercicios) { nome ->
        Text(text = nome, modifier = Modifier.padding(12.dp))
    }
}
💡

Quando trocar Column por LazyColumn: se a lista tem tamanho fixo e pequeno (ex: 3 botões do menu), Column normal é mais simples e suficiente. Se a lista vem de uma API, banco de dados, ou pode crescer sem limite (histórico de cliques, resultados de busca), use LazyColumn.

Scaffold — o "esqueleto" padrão de tela
Scaffold(

    floatingActionButton = {
        FloatingActionButton(onClick = { /* nova transação */ }) {
            Icon(Icons.Default.Add, contentDescription = "Adicionar")
        }
    }
) { paddingInterno ->
    Column(modifier = Modifier.padding(paddingInterno)) {
        // conteúdo da tela entra aqui
    }
}
⚠️

Detalhe que gera bug comum: o Scaffold entrega um paddingInterno no lambda de conteúdo — ele existe para o conteúdo não ficar escondido atrás da TopAppBar. Esquecer de aplicar esse padding (ou aplicar em cima de outro Modifier.padding conflitante) é a causa mais comum de "meu botão sumiu atrás da barra".

Segurança de Tipos boas práticas kotlin

Todo campo de texto do Compose entrega uma String — mesmo quando o usuário digita números. Converter essa String de forma insegura é a causa nº 1 de crash nos desafios práticos.

❌ inseguro
val pesoNum = peso.toDouble()
// crasha se peso == ""
✅ seguro
val pesoNum = peso.toDoubleOrNull() ?: 0.0
// campo vazio -> 0.0, sem crash

toDoubleOrNull() retorna null em vez de lançar exceção quando a conversão falha. O operador Elvis ?: completa a frase: "e se der null, use este valor padrão". É o mesmo padrão em todos os três roteiros (IMC, juros compostos, conversor de temperatura).

Erros de Build: AAR Metadata troubleshooting

Esse erro não é sobre o seu código Kotlin — é sobre versões de dependências não baterem com o SDK configurado no projeto.

Erro no Android Studio
5 issues were found when checking AAR metadata:
  - Dependency 'androidx.activity:activity-compose:1.12.0' requires
    libraries and applications that depend on it to compile against
    version 36 or later of the Android APIs.
    :app is currently compiled against android-35.

Por quê: bibliotecas recentes usam recursos da API 36. O Gradle vê que seu compileSdk está em 35 e bloqueia a build por segurança — o app poderia chamar código que o SDK 35 nem conhece.

Como resolver (estabilidade > versão mais nova): em vez de subir para a API 36 — que pode estar em fase Preview/Beta e instável — faça o downgrade das dependências no gradle/libs.versions.toml para versões 100% compatíveis com a API 35.

gradle/libs.versions.toml
[versions]
coreKtx = "1.15.0"            # reduzido para consistência com SDK 35
lifecycleRuntimeKtx = "2.8.7"  # reduzido
activityCompose = "1.9.3"      # compatível com SDK 35
composeBom = "2024.09.00"
🔨

Depois de editar o TOML, clique em Sync Now (ícone do elefante com a seta azul, no topo do editor) para o Gradle reprocessar as dependências.

Os 3 roteiros na prática

Mesma arquitetura, três domínios diferentes. Veja onde cada conceito acima aparece em cada roteiro.

enum Tela 3 mini-apps: Contador, Conversor, Dado nível: introdutório

A atividade mais guiada das três: entrega o menu completo, um mini-app 100% resolvido (TelaContador) como modelo, e ensina a criar stubs vazios para não travar a compilação antes dos desafios.

Stub — técnica anti-erro de compilação
@Composable fun TelaConversor(onVoltar: () -> Unit) { /* Desafio 1 */ }
@Composable fun TelaDado(onVoltar: () -> Unit) { /* Desafio 2 */ }

Desafio Conversor: aplica segurança de tipos (toDoubleOrNull()) na fórmula F = (C * 1.8) + 32. Desafio Dado: introduz (1..6).random() e um if dentro de Composable para o bônus do "6 comemorativo".

enum TelaFinanceira Juros Compostos + Conversor de Moedas nível: intermediário

É a única com a seção "Transição Histórica" (XML+Intents vs. Compose+State) por escrito, e a única com um Troubleshooting Guide dedicado a erros de código — não só de build.

State Hoisting na tela de resumo
@Composable
fun TelaResumo(onNavegar: (TelaFinanceira) -> Unit) {
    Button(onClick = { onNavegar(TelaFinanceira.JUROS_COMPOSTOS) }) {
        Text("Calculadora de Juros")
    }
}

Desafio Juros: três campos de estado independentes (Capital, Taxa, Tempo) e a fórmula M = C * (1 + i)^t com kotlin.math.pow. Desafio Conversor: taxas fixas de câmbio — bom terreno para depois discutir "e se a taxa fosse um estado editável?".

enum TelaSaude Calculadora de IMC + Meta de Água nível: intermediário/autônomo

A única que aborda Troubleshooting de Build (AAR Metadata) — o erro de compileSdk — em vez de erros de lógica de código. Boa oportunidade para o aluno aprender a ler mensagens de erro do Gradle, não só do compilador Kotlin.

Desafio IMC
val imc = peso / (altura * altura)
// exibir com 2 casas decimais
// peso e altura via toDoubleOrNull() ?: 0.0

Desafio Água: contador simples (estado inicial 0) que multiplica por 250ml a cada clique — reforça estado numérico + recomposição sem a complexidade de parsing de texto.
